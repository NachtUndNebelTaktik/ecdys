# Tooling Revision 2 — platform capability matrix

**Observed date:** 2026-10-24. **Gate:** tooling Gate 1. **Scope:** operator-chosen native tool execution. Browser profile isolation, Electron renderer sandboxing and the existing temporary Chromium runtime are separate capabilities.

The current application has no native tool executor, manifest importer, local catalogue adapter or code-adapter host. Its website tool shelf does not establish support for any execution profile below. Gate 1 remains open for shipping native tool execution until the chosen OS/profile combination has a packaged implementation and recorded tests. An unavailable combination does not block local notes, research, browser features supported on that platform, or another verified execution profile.

## Status vocabulary

- **Available:** the required implementation and host capabilities were exercised for the named release, OS and policy. The mere presence of an OS API, executable or Docker CLI is insufficient.
- **Degrades-to:** the operator is offered a named alternative with the changed guarantees stated. No job moves to it until the operator explicitly changes its selection and confirms the new policy.
- **Unavailable-with-reason:** deny the selected job with a stable reason; keep the tool's selected profile and saved parameters intact. Never silently run it with fewer controls.

Report capability dimensions separately: launch, process-tree ownership/teardown, filesystem confinement, resource limits, network enforcement and egress observation. A single green sandbox badge must not hide a missing dimension.

## Admission and health rules

1. Registry import is data processing. It performs no version probe, executable launch, DNS lookup, repository fetch, installer execution, YAML custom-constructor execution or container image pull. A local catalogue import must read only accepted `.yaml`/`.yml` files under the operator-selected root, with symlink containment, parser and input bounds.
2. Checking that a path exists/is executable is distinct from probing its version. A version probe **executes operator-chosen code**. It must use the selected profile, validated argv, bounded time/output and declared network policy, after explicit operator action. `--version` does not make an unknown binary harmless or offline. Store actual probe evidence and failures; do not fabricate a version.
3. A missing `network.required` declaration denies execution. A false declaration is an intent, not confinement. A `process` run cannot claim enforced offline networking or a complete egress ledger solely from that field. If policy requires enforced no-network or complete egress observation, deny the run unless the selected profile supplies those capabilities. Show process egress as best-effort/unsupported where applicable.
4. `requires_privilege: true` is displayed and refused on `process`, including its health probe. It is not a grant of root, administrator access, host capabilities, unrestricted device access or a container-management socket. A sandbox/container run still needs an implemented least-privilege policy and required OS permissions; otherwise deny with a reason.
5. No shell interpretation is introduced by the executor or manifest templates. Explicit argv prevents word splitting, globbing, pipes and command substitution by that executor. It cannot prove an arbitrary operator-chosen executable never launches another interpreter; `process` explicitly trusts the binary. Import must still reject the specified shell-command forms and unknown placeholders before writing accepted tools.
6. A selected profile stays selected after a capability failure. Offer alternatives explicitly, record the operator's change, and create provenance for the policy actually used. Never inherit the old profile's confinement/audit badge after a downgrade.
7. Egress evidence identifies the real coverage and gaps, the policy, the job, the time interval and observed destinations. A container network name alone is not evidence of firewall rules or per-job traffic observation.

## Evidence required to close Gate 1

For each enabled OS/profile combination, record the core/agent version, OS build/architecture, helper/runtime version if used, effective permissions and any policy limitations. Exercise an operator-supplied owned fixture through real argv validation, launch, output streaming/capping, timeout, concurrency, process-tree cancellation, agent crash and result provenance. Add filesystem/network escape and egress-record checks for profiles claiming those controls. Verify missing runtime/capabilities produce `denied` without launching a weaker alternative.

Windows must test the creation/Job Object race, descendant lifetime, supported executable paths and AppContainer/network behavior on Windows. macOS must test its actual supported confinement/signing strategy on macOS. Missing platform evidence leaves that combination unavailable; it does not require bundling a catalogue or making Docker mandatory.

## Cloud Gate 2 and other product obligations

Cloud's key hierarchy, metadata disclosure, entitlement and synchronization threat model remain a separate gate for the optional cloud bundle only. Local notes, files, registry, console and supported browser operations must work with that bundle absent. Neither tool execution nor local registry import requires a cloud account, marketplace or sync service.

Removing tool-catalogue redistribution gates does not waive the core's own dependency licences, browser security updates, encrypted storage/recovery, route policies, fingerprint validation, Monero/payment infrastructure, team authorization or release signing requirements. It removes an upstream tool-bundle dependency; it does not certify those independent features.
